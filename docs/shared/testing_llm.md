## Уровни тестирования

### Пирамида тестов

```
        ╱  E2E  ╲          ← мало, дорого, медленно
       ╱─────────╲
      ╱ Интеграц. ╲        ← основная масса
     ╱─────────────╲
    ╱   Unit-тесты  ╲      ← много, дёшево, быстро
   ╱─────────────────╲
```

**Unit** — тестируют чистые функции и утилиты изолированно. Быстрые, стабильные, легко пишутся.

**Интеграционные** — проверяют взаимодействие модулей: хук + API, компонент + контекст, форма + валидация.

**Компонентные** — рендерят компонент в виртуальном DOM (jsdom) и проверяют поведение через взаимодействие пользователя (клик, ввод текста).

**E2E** — запускают реальный браузер и проходят сценарии от начала до конца. Самые медленные, но дают наибольшую уверенность.

### Что тестировать на каждом уровне

| Уровень | Что покрывать |
|---|---|
| Unit | Утилиты, бизнес-логика, трансформации данных |
| Интеграционные | Хуки с API, провайдеры, роутинг |
| Компонентные | Рендеринг, пользовательские взаимодействия, формы |
| E2E | Критические пользовательские сценарии (авторизация, оплата) |

### Принцип: чем выше уровень — тем меньше тестов

E2E-тесты медленные и хрупкие. Не нужно покрывать ими всё. Unit-тесты — быстрые и стабильные, их должно быть большинство.

## Ключевые принципы

### 1. Тестируйте поведение, не реализацию

Тест не должен знать о внутреннем устройстве компонента. Он проверяет: «что видит и что может сделать пользователь».

```
❌ expect(component.state.count).toBe(1)
✅ expect(screen.getByText("Count: 1")).toBeInTheDocument()
```

Если вы переписали компонент на другой хук или изменили структуру — тест не должен ломаться.

### 2. Приоритет query-методов Testing Library

Чем ближе к тому, как пользователь находит элемент — тем лучше:

1. **getByRole** — самый надёжный, отражает семантику (`button`, `heading`, `textbox`)
2. **getByLabelText** — для полей форм
3. **getByText** — для текстового контента
4. **getByTestId** — последний резерв, когда нет другого способа

### 3. Один сценарий — один тест

Каждый `it` проверяет одно конкретное поведение. Если тест падает — вы сразу понимаете, что сломалось.

```
❌ it("handles full user flow", ...) — логин → настройки → выход
✅ it("shows welcome after login", ...)
✅ it("navigates to settings", ...)
✅ it("logs out successfully", ...)
```

### 4. Изоляция тестов

Каждый тест должен быть независим. Состояние между тестами очищается:

```ts
afterEach(() => {
  vi.clearAllMocks();
  vi.restoreAllMocks();
});
```

### 5. Factory-функции для тестовых данных

Не дублируйте создание объектов — используйте фабрики:

```ts
const createUser = (overrides?: Partial<User>): User => ({
  id: crypto.randomUUID(),
  name: "Test User",
  email: "test@example.com",
  ...overrides,
});
```

Это даёт гибкость: `createUser({ role: "admin" })` — и готовый объект для конкретного сценария.

### 6. Асинхронность: ждите, а не гадайте

Никогда не проверяйте данные, которые загружаются асинхронно, синхронно. Используйте `waitFor` или `findBy*`:

```
❌ expect(screen.getByText("Alice")).toBeInTheDocument()  // FAIL — данные ещё не загрузились
✅ expect(await screen.findByText("Alice")).toBeInTheDocument()
```

## Мокирование API

### Зачем мокировать

Тесты не должны ходить в реальную сеть. Это делает их медленными, нестабильными и зависимыми от внешних сервисов.

### MSW — мокирование на сетевом уровне

MSW перехватывает HTTP-запросы на уровне Service Worker. Код компонента не знает, что работает с моком — он думает, что общается с реальным API.

**Преимущества перед прямым мокированием `fetch`:**
- Работает с любой библиотекой (axios, react-query, fetch)
- Один и тот же handler работает и в тестах, и в Storybook
- Можно переопределять ответы точечно в отдельных тестах

**Структура:**

```
src/test/
  mocks/
    handlers.ts   — базовые handlers (возвращают стандартные данные)
    server.ts     — setupServer(...handlers)
  setup.ts        — beforeAll / afterEach / afterAll
```

**Переопределение в конкретном тесте:**

```ts
it("handles server error", async () => {
  server.use(
    http.get("/api/users", () => HttpResponse.json({ error: "Server error" }, { status: 500 }))
  );
  // ... тест проверяет, что компонент показывает ошибку
});
```

Это заменяет handler только для этого теста — остальные продолжают работать со стандартным ответом.

## Тестирование Server Components и Server Actions

### Server Components

Server Components выполняются на сервере и не попадают в клиентский бандл. Тестировать их — значит вызвать как async-функцию и проверить результат рендера.

**Подход:**
1. Зависимости (БД, API) мокируются через `vi.mock()`
2. Компонент вызывается как функция: `const page = await UsersPage()`
3. Результат рендерится через `render(page)` и проверяется

### Server Actions

Server Actions — это обычные async-функции с директивой `"use server"`. Тестируются как unit-функции:

**Подход:**
1. Мокируем БД и `revalidatePath`
2. Вызываем функцию с `FormData`
3. Проверяем возвращаемый результат и вызовы моков

**Принцип:** не тестируйте фреймворк. Тестируйте валидацию, бизнес-логику и побочные эффекты (вызовы БД, revalidate).

## Визуальное тестирование

### Зачем

Обычные тесты проверяют логику, но не вид. Компонент может работать правильно, но выглядеть сломанным.

### Snapshot-тестирование

Сохраняет сериализованный DOM-снимок и сравнивает при следующих запусках.

**Когда использовать:** для стабильных, редко меняющихся компонентов (иконки, базовые UI-элементы).

**Когда НЕ использовать:** для сложных, часто меняющихся компонентов — snapshot будет ломаться при каждом рефакторе.

### Chromatic / Percy

Облачные сервисы, которые делают скриншоты в разных браузерах и сравнивают пиксельно. Интегрируются в CI и показывают diff прямо в PR.

## LLM для тестирования

### Где LLM реально помогает

**1. Генерация edge cases**

Человек обычно пишет 2-3 очевидных теста. LLM может предложить неочевидные: пустой массив, NaN, отрицательные значения, переполнение, null/undefined.

**2. Написание бойлерплейта**

Тестовые обёртки, factory-функции, настройка MSW — это рутинный код, который LLM генерирует мгновенно.

**3. Ревью существующих тестов**

LLM может найти: дублирование, хрупкие селекторы, пропущенные edge cases, нарушение принципов.

### Как писать промпты для генерации тестов

Эффективный проомпт содержит:

1. **Контекст** — что тестируем и зачем
2. **Сигнатуру** — типы, параметры, возвращаемое значение
3. **Контракт** — что функция делает (поведение, не реализация)
4. **Требования к тестам** — фреймворк, стиль, какие edge cases покрыть

```
Напиши тесты для addToCart на Vitest.
Функция: (items: CartItem[], newItem) => CartItem[]
Контракт:
- Если элемент уже есть → увеличивает quantity
- Если нет → добавляет с quantity: 1
- Не мутирует исходный массив
Edge cases: пустой массив, дубликаты, разные товары
```

### Ограничения LLM

- LLM не знает контекст вашего проекта — стиль, соглашения, специфичные требования
- Сгенерированные тесты **всегда** нужно ревьюить
- LLM склонна к избыточному мокированию и тестированию реализации
- Для сложных интеграционных сценариев LLM часто ошибается в порядке операций

### Принцип: LLM — ассистент, не автор

Используйте LLM для ускорения, но ответственность за качество тестов — на вас. Сгенерированный код проходит то же ревью, что и написанный вручную.

## Антипаттерны

### 1. Snapshot-тестирование всего

Snapshot ломается при каждом изменении разметки. Если snapshot обновляют не глядя — он теряет смысл. Используйте только для стабильных компонентов.

### 2. Тестирование деталей реализации

Тест не должен зависеть от `state`, `refs`, внутренних вызовов. Если рефакторинг ломает тест, но не ломает поведение — тест написан неправильно.

### 3. Игнорирование async/await

Синхронная проверка асинхронного результата — гарантированно flaky-тест. Всегда ждите через `waitFor` или `findBy*`.

### 4. Тотальное мокирование

Если замокировать всё — тест проверяет моки, а не код. Мокайте только внешние зависимости (API, БД), но не React, не хуки, не утилиты внутри проекта.

### 5. Хрупкие селекторы

`querySelector("div > div > span")` ломается при первом же рефакторе разметки. Используйте семантические query: `getByRole`, `getByText`, `getByLabelText`.

### 6. Зависимость тестов друг от друга

Если тесты выполняются в определённом порядке и делят состояние — это источник flaky-багов. Каждый тест должен быть автономным.

### 7. Тесты без assertions

Тест, в котором нет `expect`, ничего не проверяет — он просто выполняет код и проходит. Убедитесь, что каждый тест содержит хотя бы одну проверку.
