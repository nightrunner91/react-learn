## Что такое SOC2 и CASA

### SOC2

SOC2 (System and Organization Controls 2) — это стандарт аудита безопасности, разработанный AICPA. Он оценивает, как компания управляет данными клиентов по пяти принципам:

1. **Security** — защита систем и данных.
2. **Availability** — доступность систем.
3. **Processing Integrity** — корректность обработки данных.
4. **Confidentiality** — конфиденциальность данных.
5. **Privacy** — защита личной информации.

Чаще всего стартапы проходят SOC2 Type II, который проверяет не только наличие политик, но и их соблюдение в течение 3–12 месяцев.

### CASA

CASA (Cloud Application Security Assessment) — программа безопасности Google для приложений, работающих с данными Google Users. Если ваше приложение использует OAuth Google, Gmail API, Google Drive API или другие чувствительные API, Google может потребовать пройти CASA.

CASA фокусируется на:

- защите данных пользователей;
- безопасной обработке OAuth-токенов;
- соответствии OWASP Top 10;
- прохождении security-оценки (в зависимости от уровня риска).

## Как security аудит касается фронтенда

Многие разработчики думают, что compliance — это задача security-команды и менеджеров. На практике аудиторы задают вопросы, которые напрямую касаются фронтенда:

- Как вы защищаетесь от XSS и CSRF?
- Где хранятся токены и сессии?
- Какие секреты попадают в клиентский бандл?
- Как вы управляете зависимостями?
- Как проводится code review?
- Как отслеживаются security-инциденты?
- Как часто обновляются фреймворки и библиотеки?

Аудитор не проверяет каждую строчку кода, но проверяет **процессы и доказательства** (evidence) того, что команда систематически управляет рисками.

## Терминология compliance

| Термин | Значение |
|--------|----------|
| **Control** | Мера защиты или процедура, снижающая риск |
| **Evidence** | Доказательство выполнения control |
| **Audit trail** | Журнал действий, позволяющий восстановить хронологию |
| **Scope** | Объём систем и процессов, охватываемых аудитом |
| **Finding** | Найденная проблема или несоответствие |
| **Remediation** | Исправление найденной проблемы |
| **Policy** | Формальное правило или руководство |
| **Procedure** | Конкретные шаги для выполнения политики |
| **Risk assessment** | Оценка рисков |
| **Vendor assessment** | Оценка безопасности поставщиков |

## Ключевые controls, важные для фронтенда

### CC6.1 — Logical access security

Контроль доступа к системам и данным. Для фронтенда:

- аутентификация и авторизация в приложении;
- защита маршрутов;
- проверка прав в Server Actions / API.

### CC6.6 — Security infrastructure

Настройка security-инфраструктуры. Для фронтенда:

- CSP;
- security-заголовки;
- HTTPS;
- WAF (Web Application Firewall).

### CC6.7 — Security incident detection

Обнаружение инцидентов. Для фронтенда:

- мониторинг ошибок (Sentry);
- CSP violation reports;
- логи подозрительных запросов.

### CC7.1 — Change management

Управление изменениями. Для фронтенда:

- code review;
- CI/CD checks;
- approval process для production-изменений.

### CC7.2 — System operations

Операции систем. Для фронтенда:

- управление секретами;
- ротация ключей;
- backup и recovery.

### CC8.1 — Change control

Контроль изменений. Для фронтенда:

- версионирование кода в git;
- pull requests;
- автоматизированные тесты.

## Рабочие процессы компаний, готовящихся к аудиту

### 1. Pull Request workflow

- Каждое изменение проходит через PR.
- Минимум один approve от другого разработчика.
- CI должен пройти: тесты, линтер, type check, security audit.
- Security-чувствительные изменения требуют дополнительного review.

### 2. Security code review

Команда выделяет паттерны, на которые нужно обращать внимание:

- новые зависимости;
- использование `dangerouslySetInnerHTML` / `v-html`;
- обработка пользовательского ввода;
- работа с cookies и токенами;
- изменения в аутентификации/авторизации.

### 3. Dependency management

- Регулярный `npm audit`.
- Dependabot / Renovate для обновлений.
- Процесс оценки новых зависимостей.
- Ведение списка одобренных библиотек.

### 4. Secret management

- Все secrets в vault / environment variables.
- `.env` файлы в `.gitignore`.
- Pre-commit hooks для поиска секретов.
- Ротация secrets.

### 5. Monitoring и alerting

- Sentry для ошибок.
- CSP reports для нарушений политики.
- Логи входов и подозрительных действий.

## Evidence: что просят аудиторы

Аудиторы просят доказательства. Для фронтенда это может быть:

| Control | Evidence |
|---------|----------|
| Code review | Скриншоты PR с approve, настройки branch protection |
| Security tests | Настройки CI с `npm audit`, отчёты сканеров |
| CSP | Скриншоты response headers, конфиг next.config.js |
| Secret management | Политика, `.gitignore`, настройки vault |
| Access control | Скриншоты настроек IAM, список пользователей с ролями |
| Dependency management | Lock-файлы, Dependabot настройки, SBOM |
| Incident response | Runbook, история инцидентов, post-mortem |

Важно: evidence должно быть **систематическим**, а не разовым. Один скриншот CSP недостаточен — нужно показать, что политика действует непрерывно.

## Access reviews

Access review — это регулярная проверка того, кто имеет доступ к системам, репозиториям, production и third-party сервисам.

### Для фронтенд-разработчика

- Проверяйте, есть ли у вас доступ к системам, которыми вы не пользуетесь.
- Не храните production credentials локально без необходимости.
- Используйте SSO и MFA везде, где возможно.

### Процесс

1. Формируется список всех систем и пользователей.
2. Руководители подтверждают, что доступ всё ещё нужен.
3. Лишний доступ отзывается.
4. Результаты документируются.

## Change management

Change management — это процесс контроля изменений в production. Для фронтенда:

- все изменения через git;
- PR + code review;
- CI/CD pipeline;
- rollback plan;
- change log или release notes.

### Экстренные изменения

Должен быть documented process для emergency changes: кто может approve, как фиксируется причина, как проводится post-review.

## Incident response

Incident response — это план действий при security-инциденте.

### Фазы

1. **Detection** — обнаружение (мониторинг, алерты, репорты).
2. **Containment** — локализация (отключение compromised систем).
3. **Eradication** — устранение причины.
4. **Recovery** — восстановление работы.
5. **Lessons learned** — post-mortem и улучшение процессов.

### Роль фронтенд-разработчика

- Уметь распознать признаки инцидента (подозрительные скрипты, CSP reports, неожиданные запросы).
- Знать, куда сообщать.
- Участвовать в расследовании, если инцидент связан с клиентским кодом.

## Penetration testing

Pentest — это имитация атаки на ваше приложение профессиональными тестировщиками.

### Виды

- **External pentest** — атака снаружи, как обычный пользователь/злоумышленник.
- **Internal pentest** — атака изнутри (с учётными данными сотрудника).
- **Web application pentest** — фокус на веб-приложении.

### Что обычно проверяют во фронтенде

- XSS (reflected, stored, DOM-based);
- CSRF;
- Open Redirect;
- insecure direct object references (IDOR);
- утечка секретов в бандле;
- слабые настройки cookies;
- отсутствие security-заголовков.

### Как подготовиться

- Провести self-assessment по чек-листам из этого раздела.
- Исправить очевидные проблемы.
- Подготовить тестовые аккаунты и документацию для пентестеров.

## Secure SDLC

Secure SDLC (Software Development Life Cycle) — это встраивание безопасности на всех этапах разработки.

### Этапы

| Этап | Действия |
|------|----------|
| **Planning** | Оценка рисков, threat modeling |
| **Design** | Secure by design, принцип least privilege |
| **Development** | Secure coding guidelines, линтеры, pre-commit hooks |
| **Testing** | Security tests, SAST/DAST, pentest |
| **Deployment** | Secure CI/CD, secret management, monitoring |
| **Operations** | Monitoring, patching, incident response |

### Threat modeling для фронтенда

Простой подход: ответьте на вопросы:

- Какие данные обрабатывает компонент?
- Откуда они приходят?
- Куда уходят?
- Что произойдёт, если данные скомпрометированы?
- Какие уязвимости типичны для такого компонента?

## Чек-лист подготовки фронтенд-разработчика

### Знания

- [ ] Понимать XSS, CSRF, CSP, secure cookies, HTTPS.
- [ ] Знать, где и как хранить токены.
- [ ] Понимать разницу между аутентификацией и авторизацией.
- [ ] Знать основные HTTP security-заголовки.
- [ ] Понимать риски зависимостей и supply chain.

### Код

- [ ] Валидировать все входные данные на сервере.
- [ ] Использовать фреймворкное экранирование по умолчанию.
- [ ] Санитизировать HTML перед `dangerouslySetInnerHTML` / `v-html`.
- [ ] Проверять авторизацию в Server Actions / API routes.
- [ ] Не хранить секреты в клиентском коде.

### Процессы

- [ ] Участвовать в code review.
- [ ] Проверять security-аспекты в PR.
- [ ] Обновлять зависимости.
- [ ] Следить за security advisories.
- [ ] Документировать architecture decisions.

### Документация

- [ ] Знать, где находятся политики безопасности компании.
- [ ] Понимать процедуру incident response.
- [ ] Иметь доступ к runbook.

## Что делать во время аудита

1. **Будьте честны.** Не преувеличивайте и не скрывайте. Аудиторы ценят прозрачность.
2. **Показывайте процессы.** Compliance — это не «у нас всё идеально», а «у нас есть процесс управления рисками».
3. **Готовьте evidence заранее.** Скриншоты, настройки CI, логи, политики.
4. **Задавайте вопросы.** Если не понимаете вопрос аудитора, попросите уточнить.
5. **Не паникуйте при findings.** Найденные проблемы — это нормально. Важно показать план remediation.

---

## Что важно понимать

SOC2 и CASA — это не просто «проверка кода». Это проверка того, что компания систематически управляет безопасностью. Фронтенд-разработчик играет важную роль: именно в его коде обрабатываются данные пользователей, токены, формы и взаимодействия с браузером.

Понимание принципов безопасности и умение объяснить свои решения аудитору — это не только требование compliance, но и профессиональная зрелость разработчика.
