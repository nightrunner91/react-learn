## Что такое Spec-Driven Development

**Spec-Driven Development (SDD)** — методология разработки, где спецификация является единственным источником истины. Разработчик описывает **что** нужно сделать, LLM генерирует **как** это реализовать, а тесты служат критерием готовности.

Это не замена TDD — это его эволюция для эры LLM. Вместо ручного написания тестов и кода, ты управляешь процессом через спецификации.

### Ключевая идея

```
Традиционный подход:  Ты → Код → Тесты → Документация
SDD:                  Ты → Спецификация → LLM → Код + Тесты
```

Спецификация заменяет сразу три артефакта:
- **Тесты** — LLM генерирует их из спецификации
- **Документация** — спецификация и есть документация
- **Требования** — всё записано явно

## Почему классический TDD умирает

### Проблема ручного TDD

Классический TDD (Red → Green → Refactor) требует:
1. Написать тест вручную
2. Запустить — он падает
3. Написать минимальную реализацию
4. Запустить — он проходит
5. Рефакторить

Это работает, но **медленно**. Одна итерация — минуты. С LLM — секунды.

### Что изменилось

| Раньше | Сейчас |
|--------|--------|
| Тесты писали люди | Тесты пишет LLM |
| Код писали люди | Код пишет LLM |
| Ручные итерации | Мгновенные итерации |
| Фокус на "как" | Фокус на "что" |

### Почему TDD не умер полностью

TDD как **принцип** (сначала тесты, потом код) жив. Но **механика** изменилась — тесты больше не пишут вручную.

## Три столпа SDD

### 1. Спецификация (ты)

Единственный источник истины. Описывает:
- Что должна делать система
- Как она себя ведёт в разных сценариях
- Какие ограничения существуют
- Что считается готовым

**Правило:** спецификация описывает **поведение**, не **реализацию**.

### 2. Генерация (LLM)

LLM превращает спецификацию в:
- Код реализации
- Тесты
- Моки и фикстуры
- Документацию (если нужно)

**Правило:** один промпт — одна генерация. Не размазывай задачу.

### 3. Верификация (тесты)

Тесты — это:
- Критерий готовности
- Обратная связь для LLM
- Документация для людей

**Правило:** без тестов нет готовности.

## Процесс разработки

### Фаза 1: Спецификация

Ты пишешь **что** нужно. Не думаешь о реализации.

```markdown
## Модуль корзины

### Функции:
- addItem(product, quantity) — добавить товар
- removeItem(productId) — удалить товар
- updateQuantity(productId, quantity) — изменить количество
- getTotal() — получить сумму

### Правила:
- Если товар уже есть — увеличивать количество
- Если quantity <= 0 — удалять товар
- Total учитывает скидки из pricing модуля
- Максимум 100 единиц одного товара

### Edge cases:
- Пустая корзина → total = 0
- Несуществующий productId → throws Error
- Quantity > 100 → throws Error

### Примеры:
addItem({ id: 1, price: 100 }, 2) → cart.items = [{ id: 1, quantity: 2 }]
getTotal() → 200
```

### Фаза 2: Генерация

Один промпт со спецификацией:

```
Реализуй модуль корзины по спецификации:
[спецификация]

Создай:
1. Реализацию (TypeScript)
2. Тесты (Vitest)
3. Типы
4. Моки для тестов

Требования к тестам:
- Покрой все кейсы из спецификации
- Edge cases обязательны
- Тестируй поведение, не реализацию
```

Результат: 5-10 файлов, 20-40 тестов за 1-2 минуты.

### Фаза 3: Валидация

```bash
npm test
```

Смотришь результат:
```
✓ Cart > addItem > adds new item
✓ Cart > addItem > increases quantity for existing item
✗ Cart > updateQuantity > throws for quantity > 100
```

### Фаза 4: Итерация

Тест упал — не чинишь сам:

```
Тест "throws for quantity > 100" падает.
Исправь реализацию. Ошибка:
[вывод теста]
```

Или добавляешь требования:

```
Добавь функцию applyPromoCode(code):
- Если код валидный — применяет скидку
- Если невалидный — throws Error
- Напиши тесты
```

### Фаза 5: Ревью

Проверяешь:
- Тесты читаются как спецификация?
- Покрывают ли бизнес-логику?
- Архитектура адекватная?
- Нет ли мусорных тестов?

## Анатомия спецификации

### Обязательные элементы

**1. Описание поведения**
```markdown
### Функция: formatDate
- Принимает: date (Date), locale (string)
- Возвращает: string
- Формат зависит от locale
```

**2. Примеры**
```markdown
### Примеры:
formatDate(new Date('2024-01-15'), 'ru-RU') → '15.01.2024'
formatDate(new Date('2024-01-15'), 'en-US') → '01/15/2024'
```

**3. Edge cases**
```markdown
### Edge cases:
- Invalid date → throws Error
- Unknown locale → uses default 'en-US'
```

**4. Ограничения**
```markdown
### Ограничения:
- Поддержка только Gregorian calendar
- Локали: 'ru-RU', 'en-US', 'de-DE'
```

### Опциональные элементы

**Контекст**
```markdown
### Контекст:
Используется в модуле отчётов для отображения дат.
```

**Зависимости**
```markdown
### Зависимости:
- Не зависит от внешних API
- Использует Intl.DateTimeFormat
```

**Производительность**
```markdown
### Производительность:
- Форматирование < 1ms
- Поддержка 1000+ вызовов в секунду
```

### Формат спецификации

**Markdown — оптимален:**
- Читаем для людей
- Понятен LLM
- Легко версионировать
- Можно хранить в репозитории

## Роль тестов в SDD

### Тесты как критерий готовности

В SDD тесты — это **definition of done**. Нет тестов — нет готовности.

```tsx
// Эти тесты = спецификация в коде
describe('formatDate', () => {
  it('formats date according to locale', () => {
    expect(formatDate(new Date('2024-01-15'), 'ru-RU')).toBe('15.01.2024')
  })

  it('throws error for invalid date', () => {
    expect(() => formatDate('invalid', 'ru-RU')).toThrow()
  })
})
```

### Тесты как верификация для LLM

LLM использует тесты как обратную связь:

```
Спецификация → LLM → Код + Тесты
                         ↓
                    Запуск тестов
                         ↓
              Прошли? → Готово
              Упали? → LLM читает ошибку → Исправляет
```

Без тестов LLM не знает, работает ли код. "Выглядит нормально" ≠ работает.

### Тесты как документация

Тесты показывают, как использовать код:

```tsx
// По тестам видно API
describe('Cart', () => {
  it('adds item with quantity', () => {
    const cart = new Cart()
    cart.addItem({ id: 1, price: 100 }, 2)
    expect(cart.getTotal()).toBe(200)
  })
})
```

### Какие тесты генерировать

**Обязательно:**
- Unit-тесты для бизнес-логики
- Интеграционные тесты для API
- Edge cases из спецификации

**Опционально:**
- Snapshot-тесты для UI
- E2E-тесты для критичных путей
- Performance-тесты для нагруженных компонентов

**Не нужно:**
- Тесты на геттеры/сеттеры
- Тесты на реализацию (internal states)
- Тесты ради покрытия

## Роль разработчика

### Что делает разработчик

**1. Пишет спецификации**
- Определяет поведение системы
- Описывает edge cases
- Формулирует критерии приёмки

**2. Валидирует результат**
- Запускает тесты
- Проверяет архитектуру
- Оценивает читаемость

**3. Итерирует**
- Уточняет спецификацию
- Добавляет новые требования
- Исправляет недопонимание

**4. Ревьюит**
- Удаляет мусорные тесты
- Улучшает архитектуру
- Следит за качеством

### Что НЕ делает разработчик

- Не пишет код руками (если не критично)
- Не пишет тесты руками
- Не отлаживает руками (LLM читает ошибки)
- Не пишет документацию (спецификация = документация)

### Новые навыки

**Spec-writing**
- Умение чётко формулировать требования
- Понимание edge cases
- Навык декомпозиции задач

**Prompt-engineering**
- Умение писать эффективные промпты
- Понимание контекста LLM
- Навык итеративного уточнения

**Review skills**
- Умение читать сгенерированный код
- Понимание архитектурных паттернов
- Навык оценки качества тестов

## Практические примеры

### Пример 1: Простая функция

**Спецификация:**
```markdown
## Функция: calculateTotal

### Поведение:
- Принимает: items (array of { price, quantity })
- Возвращает: total (number)
- Сумма = сумма(price * quantity)

### Edge cases:
- Пустой массив → 0
- Отрицательная цена → throws Error
- Нулевое количество → пропускает товар
```

**Промпт:**
```
Реализуй calculateTotal по спецификации.
Напиши тесты (Vitest), покрывающие все кейсы.
```

**Результат:**
```tsx
// LLM генерирует:
export function calculateTotal(items: Array<{ price: number; quantity: number }>): number {
  return items.reduce((sum, item) => {
    if (item.price < 0) throw new Error('Negative price')
    if (item.quantity === 0) return sum
    return sum + item.price * item.quantity
  }, 0)
}

// Тесты:
describe('calculateTotal', () => {
  it('calculates sum of items', () => {
    expect(calculateTotal([
      { price: 100, quantity: 2 },
      { price: 50, quantity: 3 }
    ])).toBe(350)
  })

  it('returns 0 for empty array', () => {
    expect(calculateTotal([])).toBe(0)
  })

  it('throws error for negative price', () => {
    expect(() => calculateTotal([{ price: -10, quantity: 1 }])).toThrow()
  })

  it('skips items with zero quantity', () => {
    expect(calculateTotal([
      { price: 100, quantity: 0 },
      { price: 50, quantity: 2 }
    ])).toBe(100)
  })
})
```

### Пример 2: Компонент

**Спецификация:**
```markdown
## Компонент: LoginForm

### Поведение:
- Форма с полями email и password
- Валидация email (формат)
- Валидация password (min 8 символов)
- При успешной отправке → вызывает onSubmit(email, password)
- При ошибке API → показывает сообщение

### Edge cases:
- Пустые поля → валидация
- Невалидный email → ошибка
- API возвращает 401 → показывает "Неверный email или пароль"
- Loading state → кнопка disabled
```

**Промпт:**
```
Реализуй LoginForm по спецификации.
Используй: React Hook Form, Zod, Testing Library.
Напиши тесты, покрывающие все кейсы.
Моки API через MSW.
```

### Пример 3: API endpoint

**Спецификация:**
```markdown
## Endpoint: POST /api/users

### Поведение:
- Создаёт нового пользователя
- Body: { email, name, password }
- Response: { id, email, name } (201)

### Валидация:
- email: валидный формат, уникальный
- name: 2-50 символов
- password: min 8 символов

### Edge cases:
- Дубликат email → 409
- Невалидные данные → 400
- Missing fields → 400
```

**Промпт:**
```
Реализуй POST /api/users по спецификации.
Используй: Next.js App Router, Zod для валидации.
Напиши тесты для всех кейсов.
Моки базы данных.
```

## Антипаттерны

### 1. Спецификация без edge cases

**Плохо:**
```markdown
## Функция: divide
- Делит a на b
```

**Хорошо:**
```markdown
## Функция: divide
- Делит a на b
- Edge cases:
  - b = 0 → throws Error
  - a = 0 → returns 0
  - Отрицательные числа → работает
```

### 2. Спецификация с реализацией

**Плохо:**
```markdown
## Функция: sort
- Используй quicksort
- Создай массив left, right
- Рекурсивно вызывай sort
```

**Хорошо:**
```markdown
## Функция: sort
- Сортирует массив по возрастанию
- Stable sort (сохраняет порядок равных элементов)
- Примеры:
  - [3, 1, 2] → [1, 2, 3]
  - [2, 1, 2] → [1, 2, 2]
```

### 3. Слепое доверие LLM

**Плохо:**
```
LLM сгенерировала код → Копируешь → Деплоим
```

**Хорошо:**
```
LLM сгенерировала код → Тесты прошли → Ревью → Деплоим
```

### 4. Тесты ради покрытия

**Плохо:**
```tsx
it('returns true', () => {
  expect(isValid('test')).toBe(true)
})

it('returns false', () => {
  expect(isValid('')).toBe(false)
})
```

**Хорошо:**
```tsx
it('returns true for valid email', () => {
  expect(isValid('user@example.com')).toBe(true)
})

it('returns false for email without @', () => {
  expect(isValid('userexample.com')).toBe(false)
})

it('returns false for email without domain', () => {
  expect(isValid('user@')).toBe(false)
})
```

### 5. Монолитная спецификация

**Плохо:**
```markdown
## Система авторизации
[500 строк всего]
```

**Хорошо:**
```markdown
## Модуль: Регистрация
## Модуль: Логин
## Модуль: Восстановление пароля
```

## Когда SDD не подходит

### Не используй SDD для:

**1. Исследовательских задач**
- Прототипирование
- Proof of concept
- Когда не знаешь, что нужно

**2. Trivial задач**
- Исправление опечатки
- Добавление константы
- Простой рефакторинг

**3. Legacy кода без тестов**
- Сначала напиши тесты для существующего кода
- Потом используй SDD для новых фич

**4. Критичных систем**
- Медицина, финансы, авиация
- Требуется ручное ревью каждой строки

### Альтернативы для этих случаев:

**Прототипирование:**
- Vibe coding (полное доверие LLM)
- Быстрые итерации без тестов

**Trivial задачи:**
- Прямое редактирование
- Copilot для автодополнения

**Legacy:**
- Characterization tests (тесты для существующего поведения)
- Постепенное покрытие

## Сравнение с другими подходами

### SDD vs TDD

| Аспект | TDD | SDD |
|--------|-----|-----|
| Кто пишет тесты | Человек | LLM |
| Кто пишет код | Человек | LLM |
| Скорость | Медленно | Быстро |
| Фокус | Как | Что |
| Итерации | Минуты | Секунды |

### SDD vs Vibe Coding

| Аспект | Vibe Coding | SDD |
|--------|-------------|-----|
| Спецификация | Нет | Есть |
| Тесты | Опционально | Обязательно |
| Контроль | Минимальный | Полный |
| Качество | Низкое | Высокое |
| Применение | Прототипы | Production |

### SDD vs BDD (Behavior-Driven Development)

| Аспект | BDD | SDD |
|--------|-----|-----|
| Формат | Given-When-Then | Markdown |
| Кто пишет | Человек + LLM | Человек → LLM |
| Автоматизация | Частичная | Полная |
| Инструменты | Cucumber, SpecFlow | Любые |

## Лучшие практики

### 1. Начинай с малого

Не пиши спецификацию на всю систему. Декомпозируй:
```
Система → Модули → Функции → Спецификации
```

### 2. Итерируй спецификацию

Спецификация — живой документ:
```
v1: Базовые требования
v2: Добавлены edge cases
v3: Уточнены ограничения
```

### 3. Используй примеры

Примеры лучше абстракций:
```markdown
### Примеры:
- calculateTotal([{ price: 100, quantity: 2 }]) → 200
- calculateTotal([]) → 0
```

### 4. Ревьюи тесты

Тесты — часть кода. Ревьюи их:
- Читаются ли как спецификация?
- Покрывают ли бизнес-логику?
- Нет ли дубликатов?

### 5. Версионируй спецификации

Храни в git:
```bash
git add specs/cart.md
git commit -m "Add cart module specification"
```

## Заключение

Spec-Driven Development — это не замена TDD, а его эволюция для эры LLM. Ключевые принципы:

1. **Спецификация — единственный источник истины**
2. **Тесты — критерий готовности**
3. **Разработчик — архитектор, а не кодер**
4. **LLM — исполнитель, а не соавтор**

SDD подходит для production-разработки, где важны качество и поддерживаемость. Для прототипов используй vibe coding, для критичных систем — ручную разработку.

Главное: SDD не отменяет необходимость думать. Ты всё ещё должен понимать, **что** строить и **почему**. LLM лишь ускоряет реализацию.
