## Почему важна стратегия рендеринга

Когда пользователь открывает страницу, HTML может появиться на экране тремя путями:

- Уже готовый на сервере или CDN — пользователь видит контент сразу.
- Генерируется на сервере в момент запроса — небольшая задержка, но контент актуальный.
- Собирается в браузере из JavaScript — долгая первая загрузка, но максимальная интерактивность после старта.

Выбор стратегии влияет на:

- **SEO** — поисковые роботы предпочитают готовый HTML.
- **Производительность** — время до первого контента и интерактивности.
- **Стоимость инфраструктуры** — серверный рендеринг стоит дороже статики.
- **Актуальность данных** — как часто пользователь видит свежий контент.
- **Сложность деплоя** — не все хостинги поддерживают SSR и ISR.

## CSR — Client-Side Rendering

### Что это

CSR — рендеринг страницы целиком в браузере. Сервер отдаёт почти пустой HTML и большой JavaScript-бандл. React, Vue или другой фреймворк в браузере строит DOM, загружает данные через API и отрисовывает контент.

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  Браузер    │ ───► │  Загружает  │ ───► │  JS рендерит│
│  запрашивает│      │  HTML + JS  │      │  страницу   │
│  страницу   │      │  (пустой    │      │  в браузере │
│             │      │  HTML)      │      │             │
└─────────────┘      └─────────────┘      └─────────────┘
                          │
                          ▼
                   ┌─────────────┐
                   │  API-запросы│
                   │  за данными │
                   └─────────────┘
```

### Когда использовать

- Личные кабинеты, админки, дашборды.
- Приложения, где SEO не важен.
- Интерактивные SPA с богатым клиентским состоянием.

### Плюсы

- **Мгновенная навигация** после первой загрузки.
- **Меньше нагрузки на сервер** — основная работа в браузере.
- **Простой деплой** — любой статический хостинг.

### Минусы

- **Плохой SEO** — поисковик видит пустой HTML.
- **Долгая первая загрузка** — пользователь ждёт JS и данные.
- **Зависимость от JavaScript** — без JS страница не работает.

### Пример в Next.js

```tsx
'use client'

import { useEffect, useState } from 'react'

export default function Dashboard() {
  const [data, setData] = useState(null)

  useEffect(() => {
    fetch('/api/stats')
      .then(res => res.json())
      .then(setData)
  }, [])

  if (!data) return <div>Loading...</div>

  return <div>{data.total}</div>
}
```

## SSR — Server-Side Rendering

### Что это

SSR — рендеринг HTML на сервере при каждом запросе. Сервер выполняет компоненты, получает данные и отдаёт готовый HTML. Браузер получает страницу сразу с контентом, а затем гидратирует её — добавляет интерактивность.

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  Браузер    │ ───► │   Сервер    │ ───► │  Готовый    │
│  запрашивает│      │  рендерит   │      │  HTML + JS  │
│  страницу   │      │  HTML       │      │  для        │
│             │      │             │      │  гидратации │
└─────────────┘      └─────────────┘      └─────────────┘
                          ▲
                          │
                   ┌─────────────┐
                   │  БД / API   │
                   │  (данные)   │
                   └─────────────┘
```

### Когда использовать

- Персонализированные страницы.
- Контент, который меняется при каждом запросе.
- Страницы, где важны актуальные данные и SEO.

### Плюсы

- **Отличный SEO** — готовый HTML сразу.
- **Быстрая первая отрисовка** — пользователь видит контент раньше.
- **Актуальные данные** — каждый запрос получает свежий контент.

### Минусы

- **Нагрузка на сервер** — рендеринг при каждом запросе.
- **Более высокий TTFB** — сервер тратит время на рендеринг.
- **Сложнее деплой** — нужен сервер или serverless-функции.

### Пример в Next.js

```tsx
// app/page.tsx
export const dynamic = 'force-dynamic'

export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    cache: 'no-store',
  })
  const posts = await data.json()

  return (
    <ul>
      {posts.map(post => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

## SSG — Static Site Generation

### Что это

SSG — рендеринг HTML на этапе сборки. Все страницы генерируются один раз при `npm run build` и раздаются как статические файлы. Данные запрашиваются во время сборки, а не при запросе пользователя.

```
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│   npm run build │ ───► │  Сервер сборки  │ ───► │  Статические    │
│                 │      │  запрашивает    │      │  HTML-файлы     │
│                 │      │  данные и       │      │  на CDN /       │
│                 │      │  рендерит HTML  │      │  статическом    │
│                 │      │                 │      │  хостинге       │
└─────────────────┘      └─────────────────┘      └─────────────────┘
                                ▲
                                │
                         ┌─────────────┐
                         │  API / CMS  │
                         └─────────────┘
```

### Когда использовать

- Блоги, документация, лендинги.
- Маркетинговые страницы.
- Любой контент, который редко меняется.

### Плюсы

- **Максимальная скорость** — файлы отдаются с CDN.
- **Отличный SEO** — готовый HTML.
- **Низкая стоимость** — не нужен сервер для рендеринга.
- **Высокая надёжность** — статические файлы не падают.

### Минусы

- **Данные устаревают** — до следующей сборки.
- **Долгая сборка** — если страниц много.
- **Не подходит для персонализации** — страницы одинаковые для всех.

### Пример в Next.js

```tsx
// app/posts/page.tsx
export const dynamic = 'force-static'

export default async function Page() {
  const posts = await getAllPosts() // Выполняется при сборке

  return (
    <ul>
      {posts.map(post => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

### Пример в Nuxt

```vue
<!-- pages/posts/index.vue -->
<script setup>
const { data: posts } = await useFetch('/api/posts')
</script>

<template>
  <ul>
    <li v-for="post in posts" :key="post.id">{{ post.title }}</li>
  </ul>
</template>
```

Для полной статики в Nuxt используется `nuxt generate`.

## ISR — Incremental Static Regeneration

### Что это

ISR — комбинация SSG и SSR. Страница генерируется статически при сборке, но может обновляться в фоне с заданной периодичностью или по запросу. Первый пользователь после истечения срока кэша получает старую версию, но в фоне генерируется новая.

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│  Запрос     │ ───► │   CDN /     │ ───► │  Старый     │
│  страницы   │      │   кэш       │      │  HTML       │
└─────────────┘      └──────┬──────┘      └─────────────┘
                            │
                            ▼
                     ┌─────────────┐
                     │  Фоновая    │
                     │  регенерация│
                     │  HTML       │
                     └─────────────┘
```

### Когда использовать

- E-commerce — цены и наличие товаров.
- Новостные сайты — статьи обновляются периодически.
- Большие каталоги, где полная пересборка дорога.

### Плюсы

- **Скорость SSG + актуальность SSR**.
- **Не нужна полная пересборка** — обновляется одна страница.
- **Гибкость** — можно задать разное время ревалидации для разных страниц.

### Минусы

- **Пользователь может увидеть устаревший контент**.
- **Сложнее кэш-инвалидация** — нужно следить за `revalidate`.
- **Требует поддержки платформы** — не везде работает из коробки.

### Пример в Next.js

```tsx
// app/page.tsx
export const revalidate = 60

export default async function Page() {
  const response = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 },
  })
  const data = await response.json()

  return <div>{data.title}</div>
}
```

### On-Demand Revalidation

```tsx
// app/api/revalidate/route.ts
import { revalidatePath } from 'next/cache'

export async function POST(request: Request) {
  const { path } = await request.json()

  revalidatePath(path)

  return Response.json({ revalidated: true })
}
```

### Пример в Nuxt

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/blog/**': { isr: 60 },
  },
})
```

## Сравнение методов рендеринга

| Метод | Где рендерится | Когда | SEO | Скорость | Актуальность | Сложность деплоя |
|-------|---------------|-------|-----|----------|--------------|------------------|
| CSR   | Браузер       | При запросе | Плохо | Медленная FCP | Всегда | Низкая |
| SSR   | Сервер        | При запросе | Отлично | Быстрая | Всегда | Средняя |
| SSG   | Сервер сборки | При `build` | Отлично | Максимальная | При сборке | Низкая |
| ISR   | Сервер сборки + фон | При `build` и фоново | Отлично | Максимальная | Периодически | Средняя |

## CDN — Content Delivery Network

### Что это

CDN — сеть серверов, размещённых по всему миру, которая отдаёт статический контент с ближайшей к пользователю точки. Вместо того чтобы запрашивать HTML из дата-центра в США, пользователь из Москвы получает его из Москвы или Франкфурта.

```
┌─────────────┐         ┌─────────────────────────────────────────┐
│ Пользователь│         │              CDN                        │
│  из Москвы  │ ──────► │  Москва ──► Франкфурт ──► Лондон ──►   │
│             │         │  origin-сервер (если нет в кэше)        │
└─────────────┘         └─────────────────────────────────────────┘
                                ▲
                                │
                         ┌─────────────┐
                         │   Origin    │
                         │  (основной  │
                         │   сервер)   │
                         └─────────────┘
```

### Что кэширует CDN

- Статические файлы: JS, CSS, шрифты, изображения.
- Сгенерированные HTML-страницы.
- API-ответы — если правильно настроены заголовки.

### Преимущества

- **Низкая задержка** — контент ближе к пользователю.
- **Разгрузка origin-сервера** — повторные запросы не доходят до него.
- **Высокая доступность** — CDN выдерживает пиковые нагрузки.
- **Защита от DDoS** — многие CDN фильтруют вредоносный трафик.

### Популярные CDN

- Cloudflare
- Fastly
- AWS CloudFront
- Vercel Edge Network
- CloudFront (AWS)
- KeyCDN

## Edge Functions и Edge Runtime

### Что это

Edge Functions — это небольшие функции, которые выполняются не на основном сервере, а на узлах CDN, ближе к пользователю. Они запускаются в легковесном runtime, обычно на основе V8 Isolates.

```
┌─────────────┐      ┌─────────────────┐      ┌─────────────┐
│  Пользователь│ ───► │  Edge Location  │ ───► │  Edge       │
│             │      │  (CDN-узел)     │      │  Function   │
└─────────────┘      └─────────────────┘      └──────┬──────┘
                                                     │
                                                     ▼
                                              ┌─────────────┐
                                              │  Origin /   │
                                              │  API        │
                                              └─────────────┘
```

### Отличие от обычных serverless-функций

| Характеристика | Edge Functions | Serverless Functions |
|----------------|----------------|----------------------|
| Расположение | CDN-узлы по миру | Один или несколько регионов |
| Холодный старт | ~0-5 мс | ~100-500 мс |
| Runtime | V8 Isolate (ограниченный) | Node.js (полный) |
| Размер бандла | 1-4 MB | Больше |
| Память | 128 MB | 512 MB - несколько GB |
| API | Web API | Node.js API |

### Когда использовать Edge Functions

- Middleware: аутентификация, геолокация, редиректы.
- A/B тестирование.
- Персонализация на уровне edge.
- Кратковременные API-эндпоинты с низкой задержкой.

### Когда НЕ использовать

- Тяжёлые вычисления.
- Работа с файловой системой.
- Большие зависимости.
- Долгие операции.

### Пример middleware в Next.js

```tsx
// middleware.ts
import { NextResponse } from 'next/server'

export function middleware(request: Request) {
  const country = request.geo?.country || 'US'

  if (country === 'RU') {
    return NextResponse.redirect(new URL('/ru', request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
}
```

### Пример в Nuxt

```ts
// middleware/geo.global.ts
export default defineNuxtRouteMiddleware((to, from) => {
  const headers = useRequestHeaders()
  const country = headers['cf-ipcountry'] || 'US'

  if (country === 'RU' && to.path !== '/ru') {
    return navigateTo('/ru')
  }
})
```

## HTTP-заголовки и кэширование

### Cache-Control

Заголовок `Cache-Control` управляет тем, как долго и где хранится ответ.

```http
Cache-Control: public, max-age=0, must-revalidate
```

Значения директив:

| Директива | Значение |
|-----------|----------|
| `public` | Можно кэшировать и в браузере, и на CDN |
| `private` | Кэшировать только в браузере |
| `no-store` | Не кэшировать вообще |
| `no-cache` | Кэшировать, но каждый раз ревалидировать у origin |
| `max-age` | Сколько секунд ответ считается свежим в браузере |
| `s-maxage` | Сколько секунд ответ считается свежим на CDN |
| `must-revalidate` | После истечения срока обязательно проверять свежесть |
| `stale-while-revalidate` | Можно отдавать устаревший ответ, фоново обновляя |

### Примеры

**Статические ассеты с длинным кэшем:**

```http
Cache-Control: public, max-age=31536000, immutable
```

**ISR-страница:**

```http
Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate
```

**Персонализированная страница:**

```http
Cache-Control: private, no-store
```

### ETag и Last-Modified

Для условных запросов сервер может вернуть:

- `ETag` — хэш содержимого.
- `Last-Modified` — время последнего изменения.

Браузер при повторном запросе отправляет `If-None-Match` или `If-Modified-Since`. Если ресурс не изменился, сервер отвечает `304 Not Modified`.

## Как выбрать стратегию

| Сценарий | Рекомендуемая стратегия |
|----------|------------------------|
| Блог, документация, лендинг | SSG или Static Export |
| Маркетинговый сайт с редкими обновлениями | SSG |
| E-commerce | ISR или SSR с кэшем |
| Новостной сайт | ISR или SSR |
| Личный кабинет, дашборд | CSR |
| Персонализированные страницы | SSR или PPR |
| Глобальное приложение с низкой задержкой | SSG + CDN + Edge Functions |
| Админка внутри компании | CSR |

### Практический пример архитектуры

```
┌─────────────────────────────────────────────────────────────┐
│                         Пользователь                         │
└────────────────────┬────────────────────────────────────────┘
                     │
                     ▼
            ┌─────────────────┐
            │   Edge Function │  <- аутентификация, A/B, geo
            │   (middleware)  │
            └────────┬────────┘
                     │
                     ▼
            ┌─────────────────┐
            │       CDN       │  <- кэш статики и ISR
            └────────┬────────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │  SSG    │  │  ISR    │  │  SSR    │
   │  страницы│  │  страницы│  │  страницы│
   └─────────┘  └─────────┘  └─────────┘
        │            │            │
        └────────────┼────────────┘
                     │
                     ▼
            ┌─────────────────┐
            │   API / БД      │
            └─────────────────┘
```

## Заключение

Выбор стратегии рендеринга — это компромисс между скоростью, актуальностью, стоимостью и сложностью.

**Ключевые выводы:**

1. **CSR** — для интерактивных приложений без SEO.
2. **SSR** — для персонализации и актуальных данных.
3. **SSG** — для быстрых, дешёвых, SEO-оптимизированных сайтов.
4. **ISR** — для баланса скорости и актуальности.
5. **CDN** — ускоряет доставку любого статического контента.
6. **Edge Functions** — добавляют логику ближе к пользователю, но не заменяют полноценный сервер.

На собеседовании важно не просто назвать аббревиатуры, а объяснить, в каких сценариях что применять и какие компромиссы возникают.
